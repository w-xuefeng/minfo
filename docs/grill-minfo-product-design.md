# MINFO 产品设计 Grill-Me 检查点

> **2026-11-12 歌词槽位最终状态覆盖决定：** 所有浏览器导出只生成新副本，绝不就地修改源文件。歌词读取由独立的**源格式能力配置**驱动：解析器用容器、编解码器和原生标签类型选择 MP3、M4A、ADTS AAC 或 generic 回退规则，绝不从扩展名、当前输出目标或歌词内容猜测。MP3/AAC 的受支持 ID3 普通/同步歌词、语言辅助字段和语言限定键进入槽位；M4A 只将 `©lyr` 读为一份 `und` 普通歌词。歌词槽位集合成为唯一事实来源与导出意图：导出会清除或不携带目标格式可表达范围内的已识别源歌词标签/帧，再由另一个目标格式歌词能力配置写入普通歌词；用户删除一个语言槽位，就明确要求新副本不再保留该语言的旧歌词。`SYLT` 的生成、事件级语义与字节级保真验证仍不在范围内，但已识别的 `SYLT` 不再作为隐藏的未受管理内容保留：重写歌词时会移除它，并将当前槽位的 LRC 原文作为普通歌词写入。已验证浏览器路径只回读该格式声明为可表达的歌词字段；容器、音频流或可回读字段失败时取消下载，格式本来无法承载的语言/附加槽位则明确为确认后的降级。输入探测不完整或非首发路径仍会明确标为无法逐项验证的降级，而源文件始终不被修改。下文关于 `SYLT + USLT` 生成、逐帧保真或“检测后阻止”的问答仅保留为历史推演，全部以本覆盖决定为准。

## Shape & Settled Decisions

> **实施更新（2026-11-11）**：浏览器输出格式矩阵固定为 MP3、M4A 和原始 ADTS AAC（`.aac`）。浏览器格式选择器不再显示其他格式或自定义扩展名；它们仅保留在本机 FFmpeg 命令路径中。主动选择 AAC 必须输出 `.aac`，不再输出 AAC-in-M4A。浏览器格式目录与表单可编辑能力配置分离维护：目标格式先于元数据表单选择，组件不得写死格式名称分支；AAC 的配置禁用封面集合编辑并说明 ADTS 限制。本文 Question Log 中与这些更新冲突的早期结论仅保留为决策历史，已被本更新取代。

- 主题：在实施前压力测试 MINFO 的产品与技术设计。
- 产品形态：部署在 GitHub Pages 的单页、纯浏览器端音频元信息管理工具。
- 首发主用户：项目作者本人，一名资深程序员与音乐制作者；核心价值是以可视化界面替代频繁手写本地 FFmpeg 命令，并在未安装 FFmpeg 的设备上保留浏览器内处理能力。
- 数据边界：用户文件默认不上传；源文件不被就地修改，导出产生新文件。
- 分层：Vue UI 与媒体服务层分离；媒体服务优先使用 Web Native 的基础能力，完整容器元数据读写和转码由 Dedicated Worker 中的 `ffprobe` / `ffmpeg` WASM 兜底。
- 发布：`main` 保存源码与文档；Actions 构建产物到孤儿 `pages` 分支，GitHub Pages 从该分支根目录部署。
- 封面替换：仅 PNG、JPG/JPEG、GIF、WebP，最大 2 MB（2,000,000 bytes），宽高均不超过 1000 px。
- 歌词：保留原文；识别 LRC 行级时间标签仅用于预览，不自动转换为同步歌词编码。
- 并行工作流：导出区需要提供“复制 FFmpeg 命令”。浏览器标准文件选择不会暴露用户文件的真实绝对路径，因此命令中的源音频、替换封面和输出路径需要由用户在本地终端补全或替换占位符。
- 命令方言：首版提供可显式切换的 `zsh/bash` 与 Windows PowerShell 模板；不得只依赖浏览器平台推断，两个模板均需独立测试引用和转义规则。
- 命令路径：现阶段采用显式路径模式。导出区提供可选的本地源音频、替换封面和输出路径输入框；用户填写的值直接进入所选 shell 方言的命令，浏览器不验证文件是否存在。
- 多封面命令路径：每张新增或替换的图片在 UI 中均有独立、可选的本地路径输入。复制脚本为每张图片声明具名变量并逐一执行占位符/空值校验；未改动的源内嵌图片随源文件保留，不需要虚构本地图片路径。
- 命令占位符保护：复制脚本在调用 FFmpeg 前验证每个必填变量；空值或仍为 MINFO 占位符时，以非零退出码和明确变量名称终止，不尝试执行 FFmpeg。复制不因路径未填而被禁用，但不允许依赖 FFmpeg 的模糊文件不存在错误。
- 命令复制形态：复制 `zsh/bash` 或 PowerShell 小型脚本，而非只有一行命令。脚本顶部声明输入、封面和输出路径变量；已填写值自动带入，缺失值保留为明确占位符，FFmpeg 命令仅引用变量。
- 命令与浏览器计划一致性：复制的本机 FFmpeg 脚本必须复现浏览器已预检计划中的目标容器、编码器/预设、元数据映射、已确认损失和覆盖策略。仅当用户主动选择标为“本机 FFmpeg 未验证”的自定义格式时，脚本可脱离浏览器能力保证；该例外必须可见。
- 本机脚本产物验收：脚本在 FFmpeg 成功后自动验证输出文件存在、`ffprobe` 能解析、目标容器与音频流符合计划，并生成可读的 `ffprobe` JSON 报告用于元数据核对。它必须明确标记为非浏览器级的完整语义验收，不能用脆弱 shell 文本解析声称验证了复杂 Unicode、多槽位或换行元数据。
- 命令渲染安全：`zsh/bash` 与 PowerShell 分别生成安全的变量或编码声明，完整保留除 NUL 外的路径与文本元数据（包括 Unicode、引号、变量符号与换行）。用户内容不得经 `eval` 或字符串拼接再次被 shell 解释；含 NUL 的值以字段级错误拒绝。渲染器必须以两种 shell 的金样本覆盖特殊字符。
- 命令渲染验证：对 `zsh/bash` 与 PowerShell 同时执行脚本文本快照和真实解释器测试；后者以假的 `ffmpeg` 捕获最终 argv。案例覆盖占位路径、正常路径、空格/Unicode、引号与 `$`/反引号等特殊符号、换行歌词、缺失字段、覆盖开关、同容器与转码计划，不把真实 FFmpeg 编码耦合进渲染器测试。
- 命令执行矩阵：脚本 argv 捕获回归必须在 Ubuntu `bash`、macOS `zsh`、Windows PowerShell 5.1 和 PowerShell 7 四种真实解释器环境运行；跨平台语法相似不能替代实际解释器证据。
- 输出覆盖：命令复制区提供“允许覆盖”显式开关，默认关闭。关闭时脚本使用 `ffmpeg -n`，开启时使用 `ffmpeg -y`；不依赖交互式终端提示。
- 源文件变更检测：每次重新分析或开始导出前比较文件名、大小和修改时间。发现变化时冻结该队列项，要求重新分析并重新确认草稿，而不继续处理旧快照。
- 外部变更合并：重新分析后使用字段级三方合并。未编辑字段采用新文件值，仅本地编辑字段保留草稿；同一字段的双方变更必须逐项解决，范围包括封面、歌词和原始标签。
- 风险确认作用域：未知标签省略、封面删减、歌词结构替换、ID3 升级与同步歌词降级等确认只绑定当前队列项的精确导出计划，包括源文件身份、草稿版本、目标容器/编码、运行时能力和损失清单。任一因素变化都必须重新确认。检测到 `SYLT` 时进入确认路径，而不是直接标记为浏览器不支持。
- 风险确认无障碍：数据损失与格式转换确认使用结构化面板，逐项列出影响、原因与保留/省略选择；支持键盘逐项操作、明确初始/返回焦点和非颜色状态标识。最终确认内容必须记录在该队列项的精确导出计划中。
- 封面兼容性：即使目标容器对 GIF/WebP 等源封面不具备可靠支持，也不自动转换或预先阻止；Web WASM 与复制的本机 FFmpeg 命令均使用原图尝试，失败后展示真实错误。
- 普通歌词写入：为保证 Web 与复制 FFmpeg 脚本一致，歌词槽位集合始终是最终导出清单。导出先清除输入中已识别的歌词标签或帧及其 FFmpeg 映射键，再由格式歌词能力配置决定写入键与回读范围：MP3/ADTS AAC 可写入主歌词、语言辅助字段与附加语言槽位，M4A 只写主歌词到 `©lyr`。已验证浏览器路径只对配置声明的可验证字段执行 FFprobe/解析器回读；M4A 的语言身份或附加槽位不因天然无法表示而取消下载，而是在执行前取得确认。LRC 时间轴不形成同步歌词产物。
- 歌词读取配置：输入歌词能力配置与输出歌词能力配置必须独立维护。前者按解析后的源容器、编解码器和原生标签类型选择可识别别名、语言来源、语言限定键、槽位上限与冲突提示；后者才决定目标的写入/回读/降级。MP3 和 ADTS AAC 使用 ID3 规则；M4A 只接受 `©lyr` 并默认 `und`；未知源使用显式 generic 回退。扩展名、MIME、歌曲内容和当前导出格式都不能改变导入映射；所有配置分支必须有格式级回归。
- 同步歌词边界：MINFO 不实现新的 `SYLT`、迁移、事件映射或语义/字节级验收。若源文件含已识别 `SYLT`，导出会移除旧帧，将当前槽位的 LRC 原文作为普通歌词写出，并将该结构性降级列为确认风险；不能把旧同步帧作为隐藏的未受管理内容保留。
- 歌词语言码：读取到的语言码默认保留；新增歌词默认使用 `und`（未指定），并提供可创建的下拉输入，常用值为 `und`、`zho`、`eng`、`jpn`。同一规范化语言只能有一个可编辑槽位；界面不依赖歌曲名、系统语言或不透明自动侦测作静默推断。
- 歌词文件导入：每个独立语言槽位提供本地“解析歌词文件”操作，仅接受不超过 2 MB 的 `.txt`、`.lrc` 与明文 QRC/XML QRC。文本和 LRC 保留原文；QRC 的逐字时间转换为行级 LRC，不能声称保留逐字同步语义。加密 QRC、空文件、错误编码和不受支持的扩展名在槽位内显示恢复建议，不改变草稿。目标槽位已有歌词时，必须通过聚焦明确的二次确认后才允许替换。
- 原生同步歌词边界：读取层把已识别同步歌词转为可编辑槽位原文与来源信息。浏览器端不重写为新的同步帧；导出会移除已识别旧帧，并以当前槽位的普通歌词为最终结果。用户若需要事件级同步帧，应使用能针对该容器明确编辑 `SYLT` 的本机工具。
- 浏览器下载命名：导出区提供可编辑的基础文件名，默认 `{源文件名} (MINFO).{最终扩展名}`；不接受路径分隔符，最终扩展名由已确认的目标容器锁定。保存位置仍完全由浏览器下载设置控制。
- 无重编码验证：同容器、仅元数据编辑的浏览器导出必须由受控执行计划强制采用 `-c copy`；首版不为每个文件再执行音频包哈希比较。该承诺须由核心格式回归矩阵和执行计划审计保障，而非在每次下载前追加全量顺序扫描。
- 产物验收：FFmpeg 成功退出不等于可交付。浏览器必须在下载前以 `ffprobe` / 元数据读取层回读产物，核对目标容器、目标音频流、请求写入的标准字段、封面、配置声明为可验证的歌词字段，以及已由用户确认的省略项；容器或音频流不完整仍阻止下载。验证边界必须来自按输出格式维护的能力配置，不能让确认后的容器固有限制再次成为下载否决。对无法由目标容器表达的歌词语言或附加槽位，确认后的降级不能被误当作回读失败。输入探测不完整或非首发路径会明确标为无法逐项验证的降级。
- 产物验收比较：标准表单字段以目标容器规范化后的语义比较；歌词键、回读级别和解析后的语言槽位检查均来自格式歌词能力配置。M4A 只要求主歌词 `lyrics`/`©lyr` 等价回读，不对不存在的 `lyrics_language` 或 `lyrics-{language}` 施加失败条件；其 `covr` 只按 PNG/JPEG 的 MIME、字节大小和集合数量回读，不要求 ID3 的封面角色或顺序。M4A GIF/WebP、ADTS AAC 封面以及跨容器高级原始标签均须在预检中逐项说明，确认后分别省略或尽力映射。标签重排、填充和等价编码变化本身不构成失败。
- 浏览器支持边界：最新桌面 Chrome / Edge 是完整受支持与回归验证环境；Firefox / Safari 按实际能力检测提供降级功能，移动端不承诺完整工作流。任何可用能力必须在界面中如实展示，不能以 UA 名称推测成功。
- WASM 线程策略：GitHub Pages 正式稳定版以单线程 FFmpeg/FFprobe WASM 为基线；本地服务和未来可选的 Cloudflare Pages 环境可在 `crossOriginIsolated` 经运行时验证后启用多线程加速。多线程不是首发功能前提，不使用 GitHub Pages 上脆弱的 Service Worker header hack。
- 媒体运行时许可证：MINFO 是个人自托管项目，不以 LGPL、GPL 或 nonfree 标签作为运行时允许/拒绝条件；许可证字段如存在只用于追溯，不构成法律判断。上游许可证仍客观存在，不能被包装层或个人使用意图抹去。
- 媒体运行时供应链：MINFO 使用 pnpm 精确锁定的 `@ffmpeg/ffmpeg` 与 `@ffmpeg/core`，构建时从已安装 core 复制同源 WASM 资产。`pnpm-lock.yaml`、冻结安装、Registry 签名校验、漏洞审计、禁用依赖安装脚本和资产 SHA-256 共同驱动发布审计与 OPFS 缓存失效。
- 媒体运行时完整性失败：绝不执行未验证、版本不匹配或第三方替代的核心。删除故障缓存后仅尝试一次同版本同源资产的重新下载与校验；仍失败则禁用浏览器媒体引擎，保留草稿、明确诊断、重试入口与复制 FFmpeg 命令路径。
- 回归测试素材：普通 MP3/M4A/ADTS AAC 与字段组合使用确定性的短音频生成器构造；仅提交少量带校验和的二进制金样本，覆盖 ID3 版本及其他难以可靠生成的边界。含 `SYLT` 的样本验证风险说明、确认门槛与确认后的副本导出，不验证帧写入或保真。测试素材不得依赖私人或受版权限制的真实音乐。
- 回归执行权威：真实 Chromium 浏览器中的 WASM Worker、OPFS 与导出产物回读是浏览器媒体能力的权威验证环境；本机 FFmpeg/FFprobe CLI 只用于辅助生成、参考或差异诊断，不能替代浏览器端到端测试。
- 核心回归矩阵策略：使用最小正交矩阵覆盖 MP3/M4A/ADTS AAC 输入与同容器/跨容器路径；每类字段至少有一个代表样本，高风险交互独立覆盖。全排列不是发布门槛，但每个已修复缺陷必须新增永久自动化回归样本。
- 核心回归样本组织：每种稳定输入变体都提供一份最大元数据样本，覆盖全部标准字段、多个值、完整日期、多评论、多封面与歌词；旧 ID3、含 `SYLT` 的不支持路径、损失确认、封面兼容性和失败路径以更小的定向样本隔离覆盖。
- 最大元数据样本变体：完整主样本固定为 MP3/ID3v2.3、MP3/ID3v2.4、AAC-in-M4A、ALAC-in-M4A 和 ADTS AAC 五份。ID3v1-only、ID3v2.2 与混合标签使用定向样本，而非复制整套富元数据夹具。
- 主样本端到端导出矩阵：MP3/M4A 主样本均须通过同容器导出；ADTS AAC 无封面样本须通过同容器重封装；固定跨容器实测为 MP3/M4A → ADTS AAC、ADTS AAC → MP3/M4A、ALAC-in-M4A → MP3（包含无损转有损确认）。AAC 目标有待保留或新增封面时必须在确认后导出不含该封面的副本。其他组合由映射与导出计划层测试覆盖。
- 音质预设端到端覆盖：对 MP3 与 ADTS AAC 两个稳定目标编码器，分别让高质量、平衡、紧凑三档预设各生成一次短音频浏览器产物；至少一条 MP3 路径使用 ALAC 源以覆盖无损转有损确认。计划层与命令渲染金样本穷尽断言所有预设的最终参数。
- 自动发布门槛：每次推送 `main` 后，只有格式化/Lint、类型检查、单元测试、核心 MP3/M4A/ADTS AAC Chromium 端到端导出回归与构建产物检查全部通过，工作流才可以更新 `pages` 分支；不得先覆盖线上页面再异步验证。
- `pages` 发布历史与回滚：`pages` 仅在首次创建时为孤儿分支，之后保留每个成功构建的提交历史。提供手动触发的回滚工作流，将 `pages` 指向指定的已验证产物提交而不修改 `main`；不以重新构建旧源码代替已验证产物回滚。
- MP3/M4A 标准字段契约：统一表单中的标题、艺术家/专辑艺术家、专辑、流派、年份、评论、曲目/碟号及总数、作曲者、封面和歌词均属于首发稳定能力。ADTS AAC 的文本字段保留须逐项回读，且其不承载内嵌封面；具体输入/目标无法表达时，预检必须取得明确的数据损失确认后生成副本，不能降格为无提示的尽力写入。
- 多值字段：艺术家、专辑艺术家和流派在草稿中始终是有序值列表。目标容器能够原生表达多值时保持该结构；否则预检必须把按目标适配器规则扁平化为单一文本列为不可逆变化，并在用户确认后才能导出。
- 发行日期：首发标准表单支持完整 ISO 日期编辑，而非仅四位年份；源文件已有的月日精度必须可见、可编辑并进入目标映射与回读验收。
- 发行日期精度：允许受控的 ISO 8601 日历精度 `YYYY`、`YYYY-MM`、`YYYY-MM-DD`；不支持时间、时区或自由文本。目标格式不能表达当前精度时，按字段级风险呈现并要求确认。
- 评论槽位：标准区只编辑一个可见的主评论；其余按语言、描述或原生标识区分的评论槽位必须在高级区列出。引擎能证明保留时保留，无法在目标表达时逐项列为风险；编辑主评论不得静默合并或删除其他槽位。
- 多封面管理：首发标准区提供完整的内嵌图片管理器，支持逐张查看、新增、替换、移除、排序与类型编辑；每张用户新选图片均适用 PNG/JPEG/GIF/WebP、2 MB、1000×1000 px 的限制。源文件已有图片不因超出新增限制而被自动删除或转码。
- 多封面映射：草稿以受控的图片类型（至少 front、back、disc、artist、other）和明确顺序建模。目标容器能表达时保留类型与顺序；只能保留图片而不能表达类型时，预检必须将类型语义丢失列为风险并取得确认。
- 多封面容量降级：目标容器或当前引擎不能承载全部图片时，预检逐张列出受影响图片及类型；用户必须明确选择保留与省略项，未完成选择不得导出。不得自动依照图片类型优先级删除内容。
- 多歌词槽位：首发提供按语言独立的歌词槽位管理器。每个语言只能有一个槽位，可单独新增、编辑、恢复或删除；`und`、`zho`、`eng`、`jpn` 是可选值，用户也可创建其他规范语言码。读取到同语言多个源槽位时按来源顺序合并为一个槽位并提示该边界。
- 多歌词写回：无论歌词是否刚被编辑，当前槽位集合都是最终导出清单。导出会先清除所有已识别源歌词标签或帧及其规范化 FFmpeg 映射，再由格式歌词能力配置写入可表达字段。通用 FFmpeg 接口不能保证辅助标签成为目标容器的原生多歌词帧：MP3/ADTS AAC 的当前路径可回读它们，而 M4A 只保留第一份普通歌词并要求确认语言身份和后续槽位的降级。浏览器只在可验证字段残留、缺失或内容不一致时取消下载。
- 多歌词来源展示：每个槽位在自己的编辑器和默认折叠的预览中标出语言、读取到的描述及来源状态。文本、语言、描述提示严格分层：只有歌词原文会进入导出标签，界面说明绝不写入歌词、复制的 FFmpeg 命令或导出文件。
- 大文件准入：不使用固定文件大小硬上限。选择文件后，结合输入大小、目标容器/编码、可用存储空间和当前运行时能力进行可行性预估；高风险或无法可靠估算时必须明确提示并要求用户确认，不把预估当作成功保证。
- 长任务控制：提供两个明确动作。`取消当前任务` 终止当前 Worker 工作、清理临时产物、保留当前草稿并自动继续队列；`停止队列` 以同样方式取消当前工作但暂停其余队列项。两者均不触碰源文件。
- 资源故障恢复：内存不足、存储配额不足或媒体 Worker 崩溃时，清理本次临时状态并重置媒体引擎；该项标记为可恢复失败，保留草稿与具体诊断，提供手动重试和复制 FFmpeg 命令，队列继续下一个独立项目，不做无条件自动重试。
- 临时媒体工作区：活动任务可将用户音频、封面和中间/输出数据暂存到 OPFS，以降低内存压力；这些字节不用于队列恢复或长期保存，任务完成、取消或失败后即删除，应用启动时也应清理遗留工作区并报告无法清理的存储问题。
- 临时工作区生命周期：不在选中文件或编辑草稿期间保留媒体副本。每次 `ffprobe` 分析或 FFmpeg 导出真正开始时才暂存所需字节，操作结束即删除；后续操作按需重新暂存源文件。
- 页面中断：媒体任务进行中，对可拦截的刷新、关闭或导航显示任务将取消的确认；若页面仍被直接终止，不假装后台继续，遗留工作区在下次启动时清理，草稿和队列上下文按既定恢复策略保留。
- 隐私与诊断：不自动上传任何遥测、媒体或元数据。用户可手动复制/下载脱敏诊断报告；默认排除音频字节、歌词、封面、标签值和本地绝对路径，分享行为始终由用户在应用外自行决定。
- 音频保真：只编辑元数据且保持原格式时，默认仅流复制/重封装，绝不静默重编码。容器无法写入请求字段时，应停止并说明限制，而不是退化为重新编码。
- Web 格式选择器：只展示首发浏览器导出矩阵中的 MP3、M4A、AAC；不显示内置候选字典、其他扩展名或自定义扩展名。它们仅属于本机 FFmpeg 命令路径，且不构成浏览器导出保证。
- 格式发布契约：浏览器端维护经过端到端回归的固定核心矩阵；当前 WASM 运行时的额外能力不会自动向浏览器格式选择器暴露。
- 首发稳定浏览器格式矩阵：MP3、M4A 和 ADTS AAC（`.aac`）。AAC 是可见的独立容器目标，不再抽象或改名为 M4A；ADTS 不承载内嵌封面，因此有待保留或新增封面时浏览器必须说明损失并在确认后导出 AAC 副本。
- MP3/M4A 稳定能力：首发保证读取、标准文本字段、封面、原始 LRC 文本歌词、同容器无重编码导出和显式 MP3↔M4A 转换。跨容器无法映射的未知标签继续按确认后省略的规则处理。
- M4A 编解码器范围：首发稳定读取、编辑与无重编码写回 AAC 和 ALAC 的 M4A；主动选择 M4A 时始终以 AAC 编码输出。其他 M4A 内编解码器不能构成浏览器导出承诺。
- AAC 输出容器：主动选择“转换为 AAC”时始终导出 ADTS `.aac`。该路径写入并回读可验证的标准文本标签；封面无法表达时列出会从副本省略的封面，经确认后导出，不能静默丢失。
- 转码音质控制：显式 MP3/AAC 转码提供有限的跨格式预设（高质量、平衡、紧凑），默认高质量。预检与复制的 FFmpeg 脚本必须显示最终解析的编码器和码率/质量参数；首发不暴露编码器私有开关。
- 转码技术参数：预设默认保留源采样率与声道数，只控制编码质量。目标编码器或容器无法表达源参数时，预检逐项说明重采样、下混或其他变化并要求确认；不得静默规范化为 44.1 kHz 双声道。
- 转码预设版本：各目标编码器的“高质量 / 平衡 / 紧凑”映射必须有独立版本。导出计划、浏览器产物验收和复制的 FFmpeg 命令均记录最终参数与预设版本；映射或运行时版本变化会使待执行计划重新预检，并须通过回归后才可发布。
- MP3 ID3 版本：保持原格式导出时尽量保持源文件可探测的 ID3v2 版本；新建或跨格式转码到 MP3 时默认写入 ID3v2.4。
- 旧 MP3 标签：ID3v1 与 ID3v2.2 属于首发稳定可编辑输入。用户首次实际修改元数据时，预检必须明确说明将升级为 ID3v2.4，并逐项列出无法映射的帧或数据；确认后才输出规范化结果。未修改的原格式路径不因此自动升级。
- AAC 容器抽象：UI 不要求用户区分裸 `.aac` 与 `.m4a`；系统根据明确的容器选择策略决定实际输出，并必须在预检与输出文件名中显示最终容器。
- AAC 输出容器：主动选择“转换为 AAC”时始终导出 `.m4a`；只有选择“保持原格式”且源文件本来为裸 `.aac` 时，才尝试保留 `.aac`。
- 自定义格式：若 Web 运行时不能确认支持，则不能用于浏览器导出；但可作为“复制 FFmpeg 命令”的目标，必须标记为“本机 FFmpeg 能力未验证”。
- 标签编辑：除标准表单字段外，首版提供高级原始元数据键值编辑器，允许新增、修改和删除可写的文本标签。
- 标签冲突：当标准表单和目标容器可映射的原始标签具有不同编辑值时，导出前逐项展示冲突并阻止导出，直至用户明确选择保留值。
- 未知标签：保持原格式且流复制时默认保留；转换格式时列出所有无法确认映射的未知/容器特定标签，用户确认后才允许省略。
- XMP `PRIV` 例外：owner-identifier 为 `XMP` 还不足以建立归因或信任；只有私有字节可解码且匹配 XMP 根元素与命名空间时才降为稳定的非阻塞信息。`x:xmptk`、`xmp:CreatorTool` 和 `adobe` 命名空间均不用于归因具体软件或厂商。已验证 XMP 不单独触发导出确认，但必须明确说明新副本不承诺逐字保留；未验证载荷仍按未知私有标签处理。
- 媒体运行时加载：页面打开时立即后台加载并初始化 FFmpeg/FFprobe WASM；OPFS 命中时复用已校验资产，未命中时立即下载和校验，而非等待用户选择文件。
- 运行时故障降级：引擎准备失败时，保留文件选择、原生基础信息、手动编辑和复制 FFmpeg 命令；浏览器导出禁用，显示持久失败状态与“重试引擎”，且明确完整分析尚未完成。
- 文件处理粒度：首版支持顺序队列。用户可加入多个文件，但 Worker 同时只分析或导出一个文件；每个文件拥有独立草稿、确认与失败状态。
- 文件导入无障碍：可键盘操作的“选择音频文件”按钮是完整主入口，拖拽区仅为增强能力。拖拽状态、拒绝原因与导入结果必须以可读状态消息宣布；任何能力不得依赖鼠标或触摸拖拽。
- 队列恢复：在支持的浏览器中持久化队列元数据、草稿和用户授权的文件句柄；页面恢复时重新检查/请求文件读取权限，不将音频字节复制到 OPFS。
- 队列恢复失败：文件句柄不可用时保留草稿并标记“需要重新关联文件”。用户重新选择文件后，应用展示文件名、大小、修改时间等身份差异，必须确认后才将草稿套用到该文件。
- 队列推进：某项失败、需要标签冲突解决或需要确认数据丢失时，该项标记为“需要处理”，队列自动继续下一个独立项目；全部项目完成后汇总待处理项。

## Question Log

### Q1 - 首发产品到底服务哪类用户？

**问题：** 当前设计隐含“桌面端个人音乐整理者”。主用户是普通用户、音乐收藏者、半专业管理者，还是其他人？

**Recommended：** 音乐收藏者/发烧友，首版单文件处理，并提供真实格式支持矩阵与字段丢失提示。

**回答：** D。项目作者本人，身份是资深程序员与音乐制作者。此前使用本地 FFmpeg 命令管理元信息，命令行效率低；MINFO 应提供可视化 UI，并在没有安装 FFmpeg 的设备上仍可在 Web 中完成处理。导出区还应有“复制 FFmpeg 命令”按钮。浏览器不能取得输入音频、替换封面、输出位置的真实本地路径，所以命令中相关路径可使用待用户替换的占位符。

**结论：** MINFO 首发是高级单用户工作台，不是面向大众的简化标签编辑器。浏览器内导出与本地 FFmpeg 命令复制是互补路径，后者必须如实表达路径占位限制。

### Q2 - “复制 FFmpeg 命令”首版支持哪种终端语法？

**问题：** 命令应只支持 macOS/Linux `zsh`/`bash`、只支持 PowerShell，还是提供可切换的双方言？

**Recommended：** 提供显式切换的 `zsh/bash` 与 PowerShell；可按平台推测默认值，但不隐藏切换。

**回答：** C。

**结论：** 首版支持 `zsh/bash` 与 PowerShell 两套命令模板，并将它们作为独立的、需回归测试的输出方言。

### Q3 - 复制命令中的路径应怎样处理？

**问题：** 应使用全部路径占位符、假定终端位于源文件目录、在 UI 中手动填写本地路径，还是提供两种模式？

**Recommended：** 同时提供“在源文件目录执行”和“显式路径”两种模式，默认前者。

**回答：** C。现阶段使用 UI 中手动填写本地路径。

**结论：** 命令复制使用显式本地路径输入框，而不是假设终端当前目录。路径值是用户自报信息，应用不会也不能验证其真实存在性。

### Q4 - 只修改元数据、且保持原格式时，默认是否绝不重编码音频？

**回答：** A。

**结论：** 音频保真优先。仅元数据变更不得在未明确发起格式转换的情况下造成重新编码或音质变化。

### Q5 - 格式下拉中的项目应当代表什么？

**问题：** 应展示所有候选项后按需探测、只展示当前已确认支持的选项、划分稳定/实验性区域，还是直接尝试后报错？

**Recommended：** 展示全部候选项但在导出前实际探测。

**回答：** B。

**结论：** Web 导出选择器只显示当前浏览器和当前 WASM 运行时已确认可用的格式；不可用格式不作为可选导出目标出现。

### Q6 - 浏览器不支持的“自定义格式”还应如何处理？

**问题：** 应移除手动输入、仅接受 WASM 可用输入、仅为复制本地命令保留，还是让浏览器直接尝试？

**结论：** 自定义格式是本地 FFmpeg 命令路径的高级逃生舱，不是 Web 端绕过能力检测的入口。

### Q7 - 是否需要“高级原始标签”编辑区？

**问题：** 标准表单之外，应只展示、可编辑或完全隐藏容器原始标签？

### Q8 - 标准表单与等价原始标签冲突时，谁生效？

**问题：** 标准字段与可映射的原始标签被改成不同值时，应静默采用标准字段、静默采用原始标签、逐项阻止并解决，还是禁止在高级区编辑映射字段？

**回答：** C。

### Q9 - 未知或容器特定原始标签如何保留？

**问题：** 未建模标签应始终尝试写入、统一丢弃、原格式自动保留但转换时确认，还是一律阻止转换？

**结论：** 完整媒体引擎是应用的常驻启动能力。页面加载即开始准备它，以换取选择文件后的最短完整分析等待时间。

### Q11 - 媒体运行时无法准备时，最低可用体验是什么？

**问题：** 引擎下载、校验或初始化失败时，应阻止整个应用、保留编辑与命令复制、只留错误页，还是降级为只读？

**Recommended：** 保留基础信息、手动编辑和命令复制，禁用浏览器导出并提供重试。

**回答：** B。

**结论：** MINFO 的本地 FFmpeg 命令路径是可靠的韧性层。浏览器媒体引擎不可用时，应用仍能帮助构造和复制可执行的本地命令。

### Q12 - 首版的文件处理粒度是什么？

**问题：** 首版应严格单文件、支持逐文件顺序队列、支持批量字段编辑，还是仅让本地命令处理批量？

**Recommended：** 支持顺序队列，每次只处理一个文件，每个文件独立编辑。

**回答：** B。

**结论：** 首版以队列降低反复选择文件的摩擦，但不引入并行 WASM 工作、统一批量覆写字段或共享草稿的复杂度。

### Q13 - 队列在刷新、关闭页面或崩溃后如何恢复？

**问题：** 队列应只保留当前会话、持久化草稿并重新匹配文件、保存文件句柄后重新授权，还是把输入音频复制到 OPFS？

**Recommended：** 仅保留当前会话，避免持久化用户音频和跨浏览器行为差异。

**回答：** C。

**结论：** 支持句柄持久化的浏览器中，队列可恢复为“待重新授权”状态。应用保存句柄与编辑上下文，不保存输入音频内容；恢复时必须重新验证权限和文件可读性。

### Q14 - 队列恢复失败时，草稿如何处理？

**问题：** 句柄不可用时应丢弃草稿、保留后要求重新关联且确认、按同名文件自动套用，还是对任意重新选择的文件自动套用？

**Recommended：** 保留草稿并要求重新关联文件，展示身份差异后明确确认。

**回答：** B。

**结论：** 编辑上下文优先保留，但文件身份不能靠文件名猜测。草稿重新应用永远是可见且需确认的操作。

### Q15 - 队列中的一项失败或需要确认时，后续项如何处理？

**问题：** 应暂停整个队列、把当前项标记后自动继续、按失败种类区别，还是先自动重试？

**Recommended：** 标记当前项为“需要处理”，继续下一个独立项，并在结尾汇总。

**回答：** B。

**结论：** 队列吞吐优先于逐项即时阻塞。它不会自动确认冲突或数据丢失，只把需要决定的工作集中回收。

### Q16 - 浏览器端首发应如何声明格式支持？

**问题：** 应只承诺回归过的核心矩阵、核心矩阵加当前运行时额外能力、完全动态，还是宽输入窄输出？

**Recommended：** 核心矩阵加“当前运行时可用”的额外格式，并对具体任务再次预检。

**回答：** B。

**结论：** 支持契约分层：核心能力可发布承诺，运行时额外能力可发现但不伪装为跨环境保证。

### Q17 - 未填写本地路径时，“复制 FFmpeg 命令”应如何工作？

**问题：** 路径不完整时应禁用复制、使用内联占位符、复制变量脚本，还是同时提供严格/草稿模式？

**Recommended：** 复制顶部声明路径变量的小型脚本，已填写值自动带入，缺失值保留占位符。

**回答：** C。

**结论：** 复制内容优先可读、可维护和跨 shell 方言一致，而不执着于单行命令。用户能在粘贴前或粘贴后完成缺失路径。

### Q18 - 输出路径已经存在时，复制的 FFmpeg 脚本应如何处理？

**问题：** 应始终拒绝覆盖、依赖终端交互、自动覆盖，还是通过默认关闭的显式开关控制？

**Recommended：** 提供默认关闭的“允许覆盖”开关，分别生成 `-n` 或 `-y`。

**回答：** D。

**结论：** 覆盖是显式的高风险操作。复制命令在无交互、批量或重定向环境下也必须有确定行为。

### Q19 - 源文件在等待、恢复或导出前被外部修改时怎么办？

**问题：** 应忽略外部变化、比较轻量身份信息后冻结、计算完整哈希，还是仅提示后继续？

**Recommended：** 在分析/导出前比较文件名、大小和修改时间；发现变化就冻结并重新分析。

**回答：** B。

**结论：** 不以昂贵的全量哈希换取少量边缘检测能力。任何可见的外部文件变化都阻止旧分析结果被继续使用。

### Q20 - 外部修改后重新分析，旧草稿如何与新文件标签合并？

**问题：** 应丢弃草稿、草稿整体覆盖、按字段三方合并，还是整体二选一？

**Recommended：** 字段级三方合并：未编辑字段接受新文件值，仅本地编辑字段保留，双方同字段变更时逐项解决。

**回答：** C。

**结论：** MINFO 必须可以与本地 FFmpeg、DAW 或其他标签工具并行使用，而不会静默覆盖任一侧有意义的修改。

### Q21 - 目标容器不可靠支持 GIF/WebP 封面时，怎么办？

**问题：** 应阻止导出、自动转换、要求显式选择，还是总是交给 FFmpeg 尝试后再报告错误？

**Recommended：** 预检后要求用户明确选择保留原图尝试、静态转换或取消，绝不自动转换。

**回答：** D。

**结论：** 原始封面优先。MINFO 不替用户篡改图像编码或动画语义，实际容器/FFmpeg 成功与否由执行结果决定。

### Q22 - 含 LRC 时间标签的歌词，目标格式没有同步歌词结构时如何写入？

**问题：** 应原样写入普通歌词字段、剥离时间标签、每次选择，还是省略歌词？

**Recommended：** 原样写入普通歌词字段，避免静默丢失同步信息。

**回答：** E。对于支持 `SYLT` 的文件格式，将带时间戳的歌词同时写入 `SYLT` 和 `USLT`；不支持时则原样写入 `USLT`。

**结论：** E 是目标语义，但它需要专用 ID3v2 写入能力。该分支已在 Q23 收束：首版不生成 `SYLT`，而是以原始 LRC 文本的普通歌词字段写入保持 Web 与 FFmpeg 命令路径一致。

### Q23 - 时间歌词的 Web 导出与“复制 FFmpeg 命令”要保持怎样的能力一致性？

**问题：** 应让两条路径都增加专用 `SYLT` 写入器、只让 Web 支持 `SYLT`、两者只写原始 LRC 至普通歌词字段，还是不为时间歌词提供复制命令？

**Recommended：** 引入专用 ID3v2 写入器，使 Web 与本地脚本都生成 `SYLT + USLT`。

**回答：** C。

**结论：** 首版坚持 FFmpeg 路径一致性。LRC 原文保留为普通歌词文本，真同步 `SYLT` 写入延后为独立功能，不能以半实现状态承诺。

### Q24 - 哪些格式必须构成“首发稳定核心矩阵”？

**问题：** 应将 MP3、M4A/AAC、FLAC、WAV、Ogg 作为核心，额外加入 ALAC、WMA/APE/AMR，还是只承诺 MP3 与 M4A/AAC？

**Recommended：** MP3、M4A/AAC、FLAC、WAV、Ogg 作为稳定核心，其余动态提供。

**回答：** D。

**结论：** 首发稳定浏览器支持刻意收窄为 MP3 与 M4A/AAC。其他格式只能在当前 WASM 运行时及具体任务通过预检时出现，不得作为上线承诺。

### Q25 - 首发稳定核心中的 “M4A/AAC” 到底指什么？

**问题：** 应稳定支持仅 M4A、M4A 与裸 AAC、只读取裸 AAC，还是让系统自行选择实际容器？

**Recommended：** 稳定核心只指 M4A，裸 AAC 仅在运行时确认后出现。

**回答：** D。

**结论：** 用户体验层将 AAC 视为一个目标类别，但实现层必须以可见、可解释的规则选择 M4A 或裸 AAC；该规则尚待决定。

### Q26 - 当用户选择“转换为 AAC”时，系统按什么规则决定实际容器？

**问题：** 应始终导出 M4A、按源扩展名继承、按编辑内容决定，还是按运行时临时决定？

**Recommended：** 主动转换到 AAC 时始终导出 `.m4a`，原格式路径才保留裸 `.aac`。

**回答：** A。

**结论：** AAC 是 UI 层目标类别，M4A 是其稳定且可预测的输出容器。输出扩展名不会因浏览器差异或是否编辑标签而悄然改变。

### Q27 - MP3 与 M4A 的“稳定核心”应保证到什么程度？

**问题：** 应仅保证基础文本和同容器导出、同时保证封面/歌词和 MP3↔M4A、承诺未知标签无损跨容器，还是只保证读取与命令复制？

**Recommended：** 标准字段、封面、原始 LRC、同容器无重编码导出与显式 MP3↔M4A；未知标签跨容器仍确认。

**回答：** B。

**结论：** 首发浏览器核心是完整的常用音乐元数据工作流，而不是仅查看标签的演示能力；但不同容器之间不能被承诺为未知私有数据的无损桥梁。

### Q28 - 写出 MP3 时，ID3v2 版本应如何选择？

**问题：** 应始终使用 ID3v2.4、始终使用 2.3、保留源版本且新文件默认 2.4，还是每次手选？

**Recommended：** 保持原格式时保留源版本，新建或转码 MP3 默认 2.4。

**回答：** C。

**结论：** MINFO 兼顾既有库稳定性和新文件 Unicode 兼容性；每个导出预检应展示实际将写入的 ID3v2 版本。

### Q29 - 歌词语言码如何确定？

**问题：** `USLT` / `SYLT` 等歌词字段可携带三字母语言码；新建或修改歌词时，应自动侦测、始终写 `und`、保留已有值并允许选择覆盖，还是从歌曲/系统语言推断？

**Recommended：** 保留已有语言码；新增歌词默认 `und`，并提供可选语言码覆盖，以避免静默误判多语或混合语言歌词。

**回答：** C。

**结论：** 语言码是明确、可见的编辑值，而不是后台猜测结果。已有文件的值保持不变；新增歌词不会因为界面语言、歌名或系统区域而被擅自归类。

### Q30 - 发现源 MP3 含有结构化 `SYLT` 时，首版如何避免误损？

**问题：** 首版不会生成新的 `SYLT`，而元数据重写/重封装未必能可靠保留这类结构化帧。若用户只改标题、封面等，也需要先定保真策略。

**Recommended：** 导出前后验证 `SYLT` 是否仍被保留；无法证明保留时阻止浏览器导出并说明原因。

**回答：** B。

**结论：** `SYLT` 是受保护的高级资料。浏览器导出必须以实际产物验证为准，而非根据预期的 FFmpeg 行为放行；验证失败或能力不足是可解释的阻止条件。

### Q31 - “保留 `SYLT`”的验证标准是什么？

**问题：** 应要求原始帧字节一致、只要求解析后的语言/时间戳/文本语义一致、只检查帧存在，还是按文件让用户选择？

**Recommended：** 每个 `SYLT` 帧的标识、标志与载荷字节必须一致；无法比较即阻止导出。

**回答：** A。

**结论：** 首版采用可审计的严格保真界线。它不把 ID3 标签重排、填充等无关变化当作失败，但绝不接受对结构化同步歌词的不可证明重写。

### Q32 - 含 `SYLT` 的 MP3 显式转换为 M4A 时怎么办？

**问题：** M4A 的正常元数据路径不能原样承载 ID3 的 `SYLT` 帧。应一律阻止、单独确认后转换并保留已有 `USLT`、增加 `SYLT` 到 LRC 的降级读取器，还是自动省略？

**Recommended：** 单独列为破坏性变化，用户明确确认后才转换；若已有 `USLT`，照常迁移它。

**回答：** B。

**结论：** 格式转换不以静默损失换便利，也不让首版承诺未完成的 `SYLT` 降级能力。用户可知情决定是否接受该跨容器限制。

### Q33 - 浏览器导出文件如何命名？

**问题：** 浏览器只能建议下载文件名，不能指定真实保存路径。应沿用源名、提供带默认值的可编辑基础名、允许完整路径输入，还是完全依赖浏览器另存为？

**Recommended：** 提供可编辑的基础文件名，默认 `{源文件名} (MINFO).{最终扩展名}`；禁止路径分隔符，扩展名由目标格式锁定。

**回答：** B。

**结论：** 下载产物与源文件清晰区分，又不会制造网页能够控制本地目录的错觉。文件名可为工作流服务，路径仍属于浏览器与操作系统权限边界。

### Q34 - “同容器仅改元数据、绝不重编码”如何验证？

**问题：** 应只信任 `-c copy` 执行计划、生成后比对音频包载荷哈希、比对解码 PCM，还是每次由用户选择？

**Recommended：** 产物生成后以流式方式比对音频包载荷哈希；不比较标签、封面等非音频数据，不一致即阻止交付。

**回答：** A。

**结论：** 首版以受控 `-c copy` 计划和回归测试兑现无重编码约束，不把一次昂贵的额外全文件扫描强加到每个浏览器导出。它必须明确记录为“执行计划保证”，而非逐文件密码学证明。

### Q35 - FFmpeg 成功退出后，浏览器是否还要回读验收产物？

**问题：** 应只依据 FFmpeg 成功退出、用 `ffprobe` 回读并阻止不符产物、回读但允许继续下载，还是只在转换格式时回读？

**Recommended：** 回读并核对目标容器、目标音频流、请求写入的标准字段、封面/歌词及已确认的省略项；不符合预期则阻止下载。

**回答：** B。

**结论：** MINFO 不把进程退出码误当作用户目标已实现。交付前的产物验收是浏览器导出可信度的必要条件，并为错误提示提供具体证据。

### Q36 - 首发浏览器支持边界是什么？

**问题：** 应以最新桌面 Chrome / Edge 为完整支持环境、要求所有现代桌面浏览器功能一致、仅支持 Chromium，还是同时把移动端作为一等目标？

**Recommended：** 最新桌面 Chrome / Edge 为完整受支持环境；Firefox / Safari 按能力检测降级，移动端不承诺完整工作流。

**回答：** A。

**结论：** MINFO 优先把复杂媒体工作流在可验证的平台做好。其他浏览器不会被虚假拒绝，但应用必须清楚呈现其实际可用的运行时、持久化与导出能力。

### Q37 - 大音频文件如何决定能否进入浏览器处理？

**问题：** 应设固定硬上限、按文件/目标/可用空间动态预估并提示、无提示接受任意大小，还是仅由用户配置固定上限？

**Recommended：** 不设伪精确硬上限；选择文件后按文件大小、目标格式、可用存储空间与运行时能力做可行性预估，风险较高时明确警告并要求确认。

**回答：** B。

**结论：** MINFO 不会把复杂的浏览器资源上限伪装成单一数字。预估负责辅助决策，实际执行仍须具备明确的失败、取消和恢复路径。

### Q38 - 用户取消长时间分析或导出时，队列如何响应？

**问题：** 应只取消当前项并继续、取消后暂停、提供“取消当前任务”与“停止队列”两个动作，还是不能真正取消？

**Recommended：** 提供两个明确动作：`取消当前任务`（继续队列）与 `停止队列`（取消当前并暂停其余）；两者都保留草稿、不触碰源文件。

**回答：** C。

**结论：** 取消是用户意图，不应被猜测为全局停止或仅局部跳过。队列控制必须可预测，并与单项失败后继续的既定策略相容。

### Q39 - 内存不足、存储配额不足或媒体 Worker 崩溃时如何处理？

**问题：** 应自动重试、清理并保留草稿供手动恢复且继续队列、丢弃草稿并暂停，还是仅显示通用错误？

**Recommended：** 清理本次临时状态、重置媒体引擎，将该项标记为可恢复失败并保留草稿；提供手动重试与复制 FFmpeg 命令，队列继续下一项。

**回答：** B。

**结论：** MINFO 把资源限制视为环境状态，而非用户编辑错误。恢复路径必须保全用户意图，并让问题能够被诊断和绕过。

### Q40 - 处理期间能否把用户媒体临时放入 OPFS？

**问题：** 应永不写入 OPFS、仅在活动任务中暂存并及时清理、持久化以支持断点恢复，还是每次由用户选择？

**Recommended：** 仅允许活动任务的临时工作区写入 OPFS；完成、取消或失败即删除，启动时清理遗留工作区，不用于恢复队列或长期保存。

**回答：** B。

**结论：** OPFS 是受控的处理工作区，不是隐形媒体库。它为大文件提供必要的空间弹性，同时不改变“用户音频不被应用留存”的产品边界。

### Q41 - 临时 OPFS 工作区何时创建、何时释放？

**问题：** 应在选中文件时创建并保留、仅在每次分析/导出运行时创建并结束即删除、从首次分析保留到导出完成，还是逐文件由用户选择？

**Recommended：** 仅在某次 `ffprobe` 分析或 FFmpeg 导出真正开始时临时建立；该操作结束就删除，后续操作需要重新暂存源文件。

**回答：** B。

**结论：** 隐私与可恢复性优先于避免一次重复复制。队列持久化的是意图和授权句柄，而非在后台滞留的媒体字节。

### Q44 - FFmpeg WASM 的线程策略如何与 GitHub Pages 共存？

### Q68 - 转码预设能否自动改变采样率或声道数？

**回答：** A。

**结论：** 格式转换已经是明确的音频变化，不能再隐含加入重采样或下混。预设的边界保持简单，技术兼容性变化保持可见。

### Q69 - 音质预设如何保持可复现？

**回答：** A。

**结论：** 可见的质量名称必须对应可审计的具体行为。运行时更新可以带来改善，但不能绕过发布测试或复用基于旧参数作出的用户确认。

### Q70 - FFmpeg / FFprobe WASM 的许可证策略是什么？

**问题：** 个人自托管项目是否要以 LGPL/GPL/nonfree 标签拦截核心，还是只保留来源和完整性要求？

**Recommended：** 不设许可证白名单；许可证信息仅用于追溯。运行时包版本必须精确锁定，且所有依赖必须通过 pnpm 的冻结锁文件、签名、漏洞和安装脚本控制。

**结论：** 运行时二进制是产品的一部分，不是可以被隐藏在 npm 包后的细节。MINFO 不提供许可证法律判断，也不因标签拒绝核心；其可执行性由 pnpm 锁文件、Registry 签名、漏洞审计、精确版本、资产哈希和回归决定。

### Q71 - 可用的 FFmpeg WASM 核心如何固定？

**问题：** 应由 MINFO 自编译最新官方源码、使用 pnpm 精确锁定的可用 ffmpeg.wasm core、运行时拉取 `latest`，还是让用户自行提供无记录核心？

**Recommended：** 使用精确锁定的 `@ffmpeg/ffmpeg` 和 `@ffmpeg/core`；每次构建从 core 包复制资产，写入版本和输出 SHA-256，并让 pnpm 对全部锁定依赖执行冻结安装、Registry 签名与漏洞审计。

**回答（后续策略变更）：** B。

**结论：** “可用的最新版 WASM 包”是一次显式、可审查的 pnpm 升级，而不是运行时的 `latest` 解析。清单将包版本、二进制身份与浏览器缓存版本统一起来。

### Q72 - WASM 运行时资产或清单校验失败时怎么办？

**问题：** 应停止执行未验证核心、删除故障缓存并仅重试一次同版本同源资产后降级，还是继续旧缓存、允许未验证核心，或从第三方 CDN 替代？

**Recommended：** 不执行任何未验证或版本不匹配的核心；删除故障缓存，尝试一次同版本的同源重新下载并校验；仍失败则禁用浏览器媒体引擎，保留草稿、重试和复制 FFmpeg 命令。

**回答：** A。

**结论：** 用户文件的处理能力不能凌驾于二进制完整性之上。故障时的高质量体验是可解释、可恢复的降级，而不是以未知代码继续运行。

### Q73 - 核心回归样本如何组织？

**问题：** 应按每种稳定输入变体维护最大元数据样本并用小样本覆盖边界、每个字段完全分拆、每种格式只保留极简样本，还是主要随机生成？

**回答：** A。

**结论：** 主样本证明完整工作流，小样本证明边界行为。两类夹具共同保持回归套件既可读、可维护，也能为数据损失问题提供清晰的失败证据。

### Q74 - 哪些输入变体必须拥有“最大元数据样本”？

**回答：** A。

**结论：** 稳定格式矩阵的每一条核心容器/编解码器路径都拥有完整资料保真的证据；历史兼容路径则以更小、更聚焦的夹具验证其明确的升级或限制行为。

### Q75 - 四份主样本的端到端导出组合如何覆盖？

**问题：** 应让四份主样本都通过同容器导出，再固定三条不同语义的跨容器路径，还是做完整交叉、仅测同容器，或跳过 ALAC 跨格式？

**回答：** A。

**结论：** 最小矩阵按不同的数据与音频语义取样，而非机械组合数量。每条端到端路径都有不可替代的价值，剩余等价排列则由更快、更精准的层级测试承担。

### Q76 - 三档音质预设怎样进入真实浏览器回归？

**问题：** 应让每个稳定目标编码器的三档预设各跑一次端到端、仅测默认高质量、三条跨容器路径各分配一种预设，还是让所有路径运行全部三档？

**Recommended：** 对两个稳定目标编码器分别让高质量、平衡、紧凑各跑一次短音频端到端导出；其中一条 MP3 路径使用 ALAC 源以同时覆盖有损确认。计划层与命令渲染再穷尽断言所有预设参数。

**回答：** A。

**结论：** 每一个发布承诺的编码器/预设组合都需要至少一次真实产物证据。短样本将这一保证维持在可持续的 CI 成本内，而不是把低频预设降为未经运行时验证的文案。

### Q77 - 命令渲染金样本应验证到什么层级？

**问题：** 应同时做脚本快照和真实解释器下的假 `ffmpeg` argv 捕获、仅做快照、用真实 FFmpeg 执行，还是仅人工检查？

**回答：** A。

**结论：** 复制脚本的正确性不能只凭字符串外观判断。MINFO 将以 shell 实际收到的参数作为安全与保真断言，同时保持该测试与媒体编码运行时相互独立。

### Q78 - 命令脚本的真实解释器/系统矩阵是什么？

**问题：** 应在 Ubuntu `bash`、macOS `zsh`、Windows PowerShell 5.1 与 PowerShell 7 都执行 argv 捕获，还是缩减到部分环境或只做本机手工验证？

### Q79 - 含未替换路径占位符的复制脚本如何失败？

**回答：** A。

**结论：** 占位符脚本仍可被安全复制和保存，但它的失败位置、原因和修复动作必须由 MINFO 定义，而不是泄漏为 FFmpeg 的环境相关报错。

### Q80 - 多封面编辑时，“复制 FFmpeg 命令”如何处理每张图片的本地路径？

**结论：** 多封面是完整的资料集合，命令路径也必须是一对一且可诊断的集合。浏览器选择图片和本地路径录入是不同权限边界，UI 需要让这一点可见。

### Q81 - 复制的本机 FFmpeg 脚本与浏览器导出计划要保持多严格的一致？

### Q82 - 复制脚本执行成功后，如何验收本机产物？

**结论：** 本机脚本应该提供足够强且可移植的结构证据，但不以脆弱的跨 shell 字符串处理冒充对复杂元数据的证明。浏览器与本机路径的验证能力边界必须如实可见。

### Q83 - 真同步歌词的第一阶段应做到哪里？

**回答：** A。

**结论：** 同步歌词是真正的二进制容器能力，不应被 FFmpeg 的普通元数据抽象稀释。先用窄而严格的 MP3 路径兑现语义，才能为以后扩展建立可信基础。

### Q84 - 有效 LRC 如何精确映射为 `SYLT` 事件？

**问题：** 应仅将有效标签精确映射为毫秒事件、统一四舍五入整秒、让无时间行继承上一时间，还是强制为每行生成事件？

**回答：** A。

**结论：** MINFO 的同步歌词语义来自可验证的用户原文，而非猜测。时间精度和无时间内容都保留在它们各自正确的数据层，避免为播放器效果牺牲资料真实性。

### Q85 - LRC 时间标签出现倒序时，后续 `SYLT` 写入器怎么办？

**回答：** B。

**结论：** 同步事件按时间顺序优先于 LRC 原始行序。稳定排序只规范 `SYLT` 派生产物，绝不重写原始 `USLT` 文本；用户必须能看到这一差异，避免误以为两者字面顺序完全一致。

### Q86 - 多条歌词落在同一时间点时，`SYLT` 如何写入？

**回答：** A。

**结论：** 资料边界高于某个播放器的展示偏好。MINFO 忠实表达 LRC 中不同事件的存在和顺序，而不是用不可见时间改写掩盖并发歌词。

### Q87 - 后续 `SYLT` / `USLT` 写入使用什么文本编码？

### Q88 - `SYLT` / `USLT` 的内容描述（content descriptor）如何使用？

### Q89 - MINFO 生成的 `SYLT` 使用哪种内容类型与时间单位？

**回答：** A。

**结论：** 同步歌词的时间基准不应因音频编码细节或不可靠内容分类而变化。LRC、解析器、写入器和产物验收以毫秒作为同一可解释坐标系。

### Q90 - 用户把带 LRC 时间标签的主歌词改成纯文本时，已有默认 `SYLT` 怎么办？

**结论：** 同步与非同步主歌词不能在未经说明的情况下分叉为不同内容。MINFO 把移除失效的同步资料视为精确、可撤销的导出决策，而不是静默副作用。

### Q91 - 后续 MP3 同步歌词能力如何触发？

### Q93 - 同一主歌词槽位的 `SYLT` 与 `USLT` 内容不一致时怎么办？

### Q94 - 新生成的 `SYLT + USLT` 如何验收？

**回答：** A。

**结论：** 生成同步歌词的验收需要证明用户关心的文本与时间语义，而不是停留在“写入了一帧”的表面信号。确定性映射也让失败可被准确定位和复现。

### Q95 - 文件选择与拖拽入口的无障碍等价行为是什么？

**问题：** 应将可键盘操作的文件选择按钮作为完整主入口并让拖拽成为增强、以拖拽为主、只支持按钮，还是只面向鼠标/触摸？

**Recommended：** “选择音频文件”按钮是完整、可键盘操作的主入口；拖拽区只是增强能力。拖拽状态、类型拒绝与导入结果通过可读状态消息宣布，任何操作都不依赖拖拽。

**回答：** A。

**结论：** 效率功能与可访问性不是互斥选项。MINFO 的高级桌面工作流保留拖拽快捷性，但用户不需要精确指针或文件拖拽支持即可完成相同导入任务。

### Q96 - 数据丢失或格式转换确认如何做到可访问、可审计？

**问题：** 应使用逐项可操作的结构化确认面板、简短复选框、仅颜色警告，还是对高级用户隐藏确认？

**Recommended：** 使用结构化确认面板：按字段逐项列出影响、保留/省略选择和原因；支持键盘逐项操作、明确初始焦点与返回焦点、非颜色状态标识，并把最终确认内容记录进该项导出计划。

**回答：** A。

**结论：** 高风险决定需要可被理解、检查和追溯，而不是被压缩成一个模糊的确认动作。无障碍行为是数据安全交互的一部分，不是导出后才补充的视觉细节。
