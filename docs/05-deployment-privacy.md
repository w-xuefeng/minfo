# 部署、隐私与运行约束

## GitHub Pages 部署

MINFO 是静态客户端应用。GitHub Pages 只发布构建产物，应用不需要也不得依赖服务器端 PHP、Ruby、Python 或转码 API。项目站点 URL 通常位于 `https://<owner>.github.io/<repository>/`，因此 Vite 的 `base` 必须按仓库路径配置。

当前工作流已经实现构建、静态产物检查、首次孤儿 `pages` 分支、带收据的发布标签和回滚；它会先以冻结锁文件安装依赖，再验证全部锁定依赖的 Registry 签名与已知漏洞，并检查生成媒体运行时的包版本和资产哈希。仓库通过 pnpm 分发单线程核心，因此浏览器导出不再因缺少自编译二进制而默认禁用；未通过完整性验证的运行时仍绝不进入产物。

### 分支约定

| 分支    | 内容                                   | 写入方式                                                       | GitHub Pages 角色                                         |
| ------- | -------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------- |
| `main`  | 源代码、`docs/`、工作流和项目配置      | 开发者正常提交与合并                                           | 不直接作为页面发布源                                      |
| `pages` | 仅 Vite 构建后的静态产物与成功部署历史 | 仅由 GitHub Actions 追加成功构建提交或由手动回滚工作流移动引用 | 在仓库 Settings 的 Pages 中选为发布分支，目录选根目录 `/` |

`pages` 仅在首次创建时是孤儿分支，因此不继承 `main` 的源码历史，也不存放源码或文档。之后每次通过质量门槛的静态产物都作为一个新的 `pages` 提交保留，形成可审计的回滚点。它禁止人工直接修改；需要回滚时，手动工作流将 `pages` 指向用户指定的、已验证的构建提交，不修改 `main`，也不在事故中重跑构建。

### 发布流程

部署工作流仅由 `main` 的 push 触发，不能由 `pages` 的更新触发，避免发布循环。后续实现的工作流应遵循以下顺序：

1. 检出触发本次构建的 `main` 提交。
2. 安装锁定版本的 Node.js 与 pnpm 依赖。
3. 运行类型检查、lint、测试和生产构建。
4. 验证构建输出目录仅含可公开的静态资产。
5. 若 `pages` 不存在，创建孤儿分支并提交构建产物；若已存在，在其当前历史上提交本次构建产物至根目录。首次孤儿检出会把触发提交的文件放入暂存区，因此必须仅在 Actions 创建的临时 `pages` worktree 中强制清空该索引和工作目录，再复制 `dist/`；不可在源码 worktree 执行这一清理。
6. 保留或生成 `.nojekyll`，避免 Pages 将 Vite 构建产物交给 Jekyll 处理。

构建任一步失败时，不更新 `pages`，线上站点继续保留最近一次成功产物。工作流需要获得向 `pages` 分支写入的最小 GitHub Actions 权限；不要把 `pages` 设为要求人工 PR 合并的受保护分支，否则自动发布会失效。

`docs/` 在本项目是 `main` 上的设计文档目录，不是 Pages 构建目录。只有 Vite 的构建输出（通常为 `dist/`）可以被同步到 `pages`，从而避免源码、测试文件、文档或开发配置被意外公开。

参考：[GitHub Pages 是静态托管服务](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[从分支配置发布源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。

## WASM 与跨域隔离

FFmpeg WASM 的多线程核心依赖 `SharedArrayBuffer`，通常要求页面使用 COOP/COEP 跨源隔离响应头。GitHub Pages 部署基线不应将该条件作为前提，所以首版必须以 **单线程 FFmpeg WASM** 作为可靠后备路径。

若日后迁移至可以一致配置响应头的托管环境，可在 `crossOriginIsolated` 为真且 WASM 资源满足跨源策略时，选择性启用多线程核心。它是性能增强，不得改变功能正确性或成为唯一转换路径。

页面进入后在后台准备同源 WASM 资产，避免用户首次导出才面对长时间初始化。浏览器原生层仍先完成文件属性和可用技术属性读取；完整嵌入元数据、格式探测、写入标签或转换由媒体服务选择受控解析器或 Dedicated Worker 中的 `ffprobe` / `ffmpeg` 路径。`ffprobe` 用于探测，`ffmpeg` 用于生成新文件，两者都不暴露在 UI 组件中。

发布运行时由 pnpm 精确锁定的 `@ffmpeg/core` 提供，并由对应的固定 `@ffmpeg/ffmpeg` 包装层加载。当前组合是 `@ffmpeg/core@0.12.10` 与 `@ffmpeg/ffmpeg@0.12.15`；它不是“官方最新 FFmpeg”的声明。构建清单记录两包的版本、已知内置 FFmpeg 基线、线程变体以及所有复制资产的长度和 SHA-256。MINFO 不再以 LGPL、GPL 或 nonfree 字段作为加载或发布拒绝条件；许可证信息可以保留用于追溯，但不能替代冻结锁文件、pnpm Registry 签名审计、漏洞审计或资产哈希。

参考：[FFmpeg WASM 的 Worker 与核心说明](https://github.com/ffmpegwasm/ffmpeg.wasm/blob/main/apps/website/docs/overview.md)、[MDN 关于 COOP 和跨源隔离](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Opener-Policy)。

## OPFS 二进制缓存

为避免站点再次使用时重新下载大型 FFmpeg/FFprobe WASM 资产，应用将**仅运行时二进制资产**缓存到 OPFS。OPFS 是当前站点源独有的浏览器存储空间，不能被用户直接当作文件夹浏览，且受浏览器存储配额与“清除站点数据”影响。

运行时缓存目录不保存用户选择的音频、封面、歌词或导出文件。产品目标是让活动分析或导出使用一个独立的临时 OPFS 工作区来降低大文件内存峰值，并在完成、失败或取消时删除；当前代码尚未实现这一用户媒体工作区，媒体暂时只进入内存和 Worker 临时文件系统。队列恢复保存意图和在浏览器允许时的文件句柄，不保存用户媒体字节。

### 缓存版本和完整性规则

- 构建流程为每个部署输出一个小型、同源的媒体运行时清单，并将其和实际核心脚本、WASM、附属 Worker 一同发布至 `pages` 分支。
- 清单包含 schema 版本、精确的 `@ffmpeg/core` / `@ffmpeg/ffmpeg` 版本、已知内置 FFmpeg 基线、线程变体、每个资产的 URL、长度与 SHA-256。应用仅接受全部字段精确匹配且哈希验证通过的 OPFS 缓存。
- 应用源码更新但媒体运行时清单不变时，复用缓存；FFmpeg、FFprobe、WASM 核心、核心变体或任一资产哈希改变时，视为新版本并重新缓存。
- 更新写入版本化暂存目录。所有文件下载和校验完成后才切换活动清单，旧的已验证缓存必须在新版本成功前保留，防止中断更新破坏可用缓存。
- 默认只保留活动版本和一个最近的已验证版本；空间不足时可只保留活动版本。不会为了缓存主动申请无限制存储或占满可用配额。
- 访问 OPFS、读取缓存或由缓存创建运行时 URL 失败时，可使用当前同源 Pages 的相同、已校验运行时网络加载。清单或资产哈希校验失败时不执行未知二进制：只重试一次同源相同版本，仍失败则禁用浏览器媒体引擎，保留草稿和复制本机脚本的恢复入口。错误消息不得泄露本地缓存路径或用户文件信息。

使用 OPFS 不构成离线应用承诺。用户清除站点数据、更换浏览器配置文件、切换 `github.io` 与自定义域名或被浏览器回收存储时，都可能需要重新下载运行时。

## 隐私承诺与实际边界

- 当前用户选择的音频、封面、歌词和导出结果仅在浏览器内存、Worker 临时文件系统和浏览器下载流程中出现；未来的活动任务临时 OPFS 工作区同样不得用于持久化或恢复。
- 应用不把文件内容上传到自建服务、分析服务或第三方转码服务。
- 不在 URL、错误上报、控制台或分析事件中记录文件名、标签、歌词、封面数据或二进制内容。
- 页面托管方仍可能按照其服务规则记录访问 IP 等标准访问日志；“本地处理”不等于用户从未访问网络，因为页面和 WASM 资源需要首次加载。
- 使用本地同源静态 WASM 资源，避免在处理用户文件时依赖未经控制的第三方 CDN。若实施时确有 CDN，必须在隐私文档和 CSP 中显式列出。
- OPFS 中只持久保留经过完整性校验的公开运行时资产；任何用户音频、封面、歌词、文件名或导出内容均不得作为持久缓存写入 OPFS。

## 性能与内存策略

浏览器端转码会受设备内存、CPU、浏览器实现、文件时长和输出编码器影响。产品不可声明固定转换速度或任意文件大小支持。

- 首次进入在不阻塞界面的后台准备重型 WASM 核心；使用前仍须等待完整性校验完成。
- 首次媒体操作优先复用经版本和 SHA-256 校验的 OPFS 运行时缓存；缓存未命中时已开始后台下载、校验和原子切换新版本，绝不使用部分下载或未知的二进制。
- 显示 WASM 初次准备状态和可取消的处理阶段，避免看似无响应。
- 用传输所有权、及时释放 Blob URL、缩略图和 Worker 临时文件减少峰值内存。
- 在导出前测量文件大小并给出资源风险提示。封面新增/替换使用固定保护阈值：2 MB（2,000,000 bytes）、宽和高均不超过 1000 px；音频文件本身的资源告警阈值仍由性能基准测试确定。
- Worker 崩溃、内存分配失败、输出过大或浏览器终止任务时，保留表单草稿，提供重试和较兼容格式建议。

## 安全基线

- 只处理用户显式选择的文件，不递归读取目录，也不索要不相关权限。
- 把文件名、歌词和标签作为不可信文本处理；在 Vue 模板中保持默认转义，禁止将它们作为 HTML 注入。
- 对新选择的封面图片依次进行大小、文件签名、图像头尺寸和受控解码检查；仅接受 PNG、JPG/JPEG、GIF、WebP，且限制为 2 MB（2,000,000 bytes）和 1000×1000 px。预览使用受控 Object URL 并及时撤销。
- 不将来自文件的元数据用于动态脚本、样式、下载 URL 或命令字符串拼接。
- 转换命令和参数由固定的目标配置生成，手动格式输入只能查询预定义/验证后的格式描述，不能成为任意 FFmpeg 参数入口。

## 浏览器支持原则

支持状态按能力而非浏览器名称决定。用户访问时检测 File API、Worker、WebAssembly、WebCodecs 与具体编解码配置；缺少 WebCodecs 不应阻止 Worker 后备路径。每个版本在 Chromium、Firefox、Safari 的当前稳定版及一台低性能移动设备上执行样本矩阵，结果写入发布记录。
